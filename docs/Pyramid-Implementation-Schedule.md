## Challenge goals and useful partial routes — clarification 20 October 2026

Challenge headers are labelled **Current/Goal counters**, never a progress bar.
`Boards cleared X/Y` counts completed boards toward target Y: a clear-three
challenge begins at `0/3`, then shows `1/3`, `2/3` and completion at `3/3`.
`Score 0/5,000` means zero points toward 5,000; `Aces cleared Current/Goal`
counts removed Aces, with corresponding labels defining other rank objectives.
Read the actual label and target; a fraction alone does not establish the goal.

Normal gameplay instead shows top-right `Boards: n of 3`, the current board
number. The built-in Solver has its own top-centre key icon, `Solver` title and
bar beneath it, and is unavailable in challenges. Its display supplies no
challenge-goal, board-clear or input authority. These semantic definitions do
not claim runtime support for arbitrary challenge labels or targets.

Charlie reports an 18-King challenge where a board with no full-clear solution
still yielded all four Kings; at 16/18, a later uncleareable board supplied the
remaining two and completed the challenge. An eighteen-King target requires at
least five full packs, since each has four Kings. This is a rank-removal goal;
a score challenge is a separate objective with an evidenced scoring rule.

Record these independent challenge contracts before changing the shared planner:

| Goal | Progress to optimise/verify | Budget and completion requirements |
| --- | --- | --- |
| Clear a specified number of boards | Positively verified tableau clears and the displayed challenge counter. | Track the observed deal allowance and challenge target; a partial removal route does not count as a cleared board. |
| Remove/match a specified number of one card value | Actual removals of the target rank, including eligible pile cards; use the remaining target rather than requiring a whole-tableau clear. | Maximise credited target removals on the available board and stop when the observed challenge target is achieved; preserve progress across validated fresh-board redeals. |
| Reach a specified score | Verified score gain under the observed scoring rules. | Respect the stated deal allowance even when the challenge permits an unlimited number of boards; card counts alone do not establish score. |

The rank-removal metric is **individual target-value cards removed**, not the
number of MATCH commands. A King removal counts one King; an Ace/Queen match
counts one Ace for an Ace challenge. DRAW and RECYCLE count zero. Count each
original card once, including playable tableau, DL and DR cards. The finder
should report total removals and target-rank removals separately, optimise the
latter for the remaining challenge requirement, and verify actual credited
progress during execution. At 16/18 Kings, two further credited Kings suffice;
a full-board clear or extra actions are unnecessary to the challenge target.

**Longest action sequence is not a removal objective.** DRAW/recycle operations
can lengthen a sequence without removing anything. Search must explicitly
maximise the useful challenge credit, then prefer fewer actions among equally
productive routes. Without a challenge objective, a separately agreed useful
partial-board route can maximise actual removals; it must not be labelled a
full-clear solution. Resource/time interruption remains unknown and is not proof
of an uncleareable board or permission to redeal.

Charlie identifies **REDEAL**, appearing after sufficient traversal of DRAW, as
the control used to proceed after useful progress. This resolves the earlier
operator question about the control's name/appearance. Before automatic use,
retain native positive control evidence and verify its exact fresh-board,
stock-pass, allowance-consumption and credited-progress effects. Keep DRAW
recycling, fresh-board REDEAL and the challenge's displayed deal budget distinct;
the number of packs needed for a rank target does not define those controls.

This extension needs an explicit xSAR objective/rules/replay contract and matching
application completion/progress verification: full-clear impossibility pruning
must not discard a board that still permits useful target removals. Preserve
full-clear defaults and independently replay every partial route under the same
agreed stock allowance. Generic reusable search belongs in xSAR; interpreting
native challenge counters, recognising REDEAL and authorising guest input remain
application policy. No challenge planner/API/control implementation or guest input
is included in the narrow 2.6.112 RECON timing correction.

```csv
SEQUENCE,ACTION,CARD1,CARD2
```

- `SEQUENCE`: one-based order of play; this recording has 48 consecutive entries,
  `1..48`. This count describes the received recording, not every possible solution.
  Charlie added it to recover the intended order if spreadsheet rows were moved.
  The proposed reader sorts by SEQUENCE in memory, preserves CARD1/CARD2 order,
  rejects duplicates or gaps and never rewrites the source recording.

Row r has columns `1..r`: apex `1|1`, second row `2|1` and `2|2`, bottom row
`7|1` through `7|7`. Valid locations satisfy `1 <= column <= row <= 7`.
Locations remain fixed when cards disappear. DL and DR denote current visible
pile tops, not immutable stock ordinals.
